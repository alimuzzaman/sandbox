# Contract: Creation and URL Ownership v1

Original request IDs retain their owner namespace, including `/`, and remain bounded to 256 ASCII characters across delivery lookup, creation context, receipt and URL-result joins. They are opaque keys, never filesystem paths. Operation, job, instance and label identifiers keep their narrower limits.

## Ensure relation

The instance owner accepts an optional CreationContext containing schema_version=1, delivery operation_id, original request_id, optional job_id, intent_digest, intent_fields, project_identity, project_root_digest and exact requested label. Existing unrelated ensure callers remain additive-compatible. Covered deploy/preview requires instance_creation_receipt_v1 before source/instance/URL effects that depend on this guarantee.

This contract covers WordPress and generic Compose, both already reachable by exposed deploy. The supported CLI path is sandbox/commands/instances_cmd.py → sandbox/application/runtime_service.py → the selected adapter; sandbox/application/context.py forwards WordPress calls to sandbox/core/_instances.py, while sandbox/runtimes/compose.py owns generic runtime commits. Carry creation_context and expected_incarnation as optional OperationRequest.arguments fields without dropping them at either closure. Selected-runtime capability checks run before adapter effects. An unsupported optional native adapter refuses the covered request; generic Compose must implement the contract and retain its supported positive exposed-deploy path.

intent_fields is a closed object containing schema_version=1, delivery_intent_digest, target_scope_digest, project_identity, project_root_digest, label, instance_config_digest and create_allowed. intent_digest is its canonical digest. The instance config digest covers resolved nonsecret configuration, runtime/PHP/WordPress overrides and config-label policy; target scope binds the registered host/machine. The owner recomputes its current resolved fields and compares the digest before effects. CreationReceipt and every transport/lookup result retain the exact frozen intent_digest. Secret values or new secret-value hashes are excluded.

The context is not deletion authority. Validate all fields and available original job/request binding before mutation. Inside the existing per-project and port/registry locks:

1. Resolve the exact project/root/label through the owner.
2. Call the instance owner's reserve_creation_request using the canonical project_identity/label scope and original request key. Persist a compact guard containing operation_id and intent_digest before any pending/selected registry commit. A used key with a changed intent/operation refuses before effects. A matching used key is lookup-only: return its exact joined current receipt, or unknown/expired when detail is missing; never repeat creation/configuration.
3. Only a newly persisted guard permits continuing the otherwise-authorized ensure. A new incarnation gets relation=created and a pending receipt atomically with its pending registry commit. An existing selected incarnation gets relation=reused for this request, committed before dependent effects.
4. Finish the existing ensure workflow and update completion from the actual result. A lost response leaves the committed receipt discoverable; an interrupted child remains pending/unknown where terminal proof is absent. Guard reservation and receipt/registry commitment are ordered across two stores, with no atomicity claim: reservation without a receipt after a crash is unknown and cannot authorize replay.

For generic Compose, add the missing pending commit before overlay/configuration/start effects under project and allocation serialization. A genuinely new owner row gets an opaque incarnation and created relation. An existing generic row retains its incarnation or, if absent, receives a present-tense opaque incarnation in the authorized guarded selection commit with relation=reused; this establishes only current selection, never historical creation or cleanup rights. This initialization requires a newly reserved request: a retained request/receipt with absent or mismatched current incarnation refuses, and no incarnation is reminted to satisfy it. Preserve that selected incarnation on ready, failed and later lifecycle writes. Do not alter WordPress W1 legacy identity refusal or unrelated ensure behavior. Runtime health is completion evidence; it must not be the first ownership commit. WordPress install snapshot capture remains the existing sandbox/commands/data.py implementation.

The owner validates schema and finite bounds in sandbox/server_config/models.py and exposes safe receipt lookup through the existing instance service boundary. No caller reads registry JSON or reconstructs creation using inventories. Store at most 32 terminal and eight pending/uncertain receipts per instance, each at most 4 KiB; a full protected set refuses new receipt admission.

sandbox/server_config/creation_requests.py owns the durable guard store at runtime/instance-creation/requests.sqlite3 on the instance controller. reserve_creation_request(scope, request_key, operation_id, intent_digest) and mode=ro read_creation_request are its only required interfaces. Guards are at most 1 KiB, limited to 4,096 per controller and an 8 MiB database plus bounded 8 MiB rollback space. They never expire, evict or disappear with instance/receipt deletion. At capacity, refuse new keys with creation_request_capacity before registry effects; existing lookups still work. Changed intent returns creation_request_conflict; matching absent/evicted detail returns creation_request_unknown/creation_request_expired. No automatic reset, compaction or namespace rotation reopens used keys; unavailable/corrupt guards fail closed.

## Remote transport and lookup

sandbox/core/_remote.py adds optional structured creation context to ensure_remote_instance and a read_remote_creation_receipt accessor. Both carry intent_digest; mutation transport also carries the closed intent_fields for owner recomputation. The authenticated remote helper uses the registered instance owner service and guard lookup, with an explicit schema/capability response; it does not run ensure to answer a lookup. Lookup key is exact project/root/label/request/operation, with expected intent_digest, not just a name.

Use bounded structured CLI context input and separate pure capability/receipt query modes on the existing ensure transport. sandbox/cli.py parsing/predispatch belongs to F; instances_cmd.py handling, runtime-service checks, application composition and both owners belong to E. Pure queries dispatch through explicit read-only owner access before compatibility/runtime writers; they do not invoke adapter ensure, render overlays, initialize/migrate repositories or read registry JSON in a caller. WordPress capability publication uses the existing composition envelope; WordPressAdapter already forwards OperationRequest. No new sandbox_core.py or other compatibility-facade consumer is needed. Unrelated callers that omit the new fields keep their existing signatures and output meaning.

Return a bounded receipt or a typed missing/expired/unsupported/conflicting result. SSH/transport timeout, malformed output, lost response or a nonterminal original child yields unknown execution/ownership where unproved. Never return created from a before/after inventory difference.

reconcile_remote_instance and set_remote_instance_url accept expected incarnation and original operation/request context for covered callers. Returned instance names alone are insufficient. Existing unrelated callers retain their current optional-argument behavior.

## URL write/readback

Covered apply first requires a succeeded creation receipt and the exact current incarnation. Before reconciliation effects it reserves a separate apply-phase deny-only guard under the original creation scope and request. This guard shares the 4,096-record/8 MiB creation store limits. A repeated covered apply returns typed unknown without repeating effects, including after a crash or a successful first apply; it cannot use ensure completion as proof of apply completion. Ordinary callers without creation context keep their existing behavior.

The frozen nonsecret configuration projection includes normalized PHP extension requirements and supported typed WordPress policy constants. Arbitrary config constants, secret values and secret-value hashes are excluded. The receipt does not claim full configuration equivalence or present runtime source identity.

The covered remote transport invokes the bounded `ensure --creation-url-json` owner mutation mode with the original creation context and expected incarnation. The instance owner holds its existing per-project lock across the writes and readback; this mode is not a pure lookup. Before each required home/siteurl write, re-read the selected exact instance through the owner and verify its incarnation. Apply only the authorized public URL to that selected instance. Read both required values back under the same expected identity and retain per-field match results.

Store at most 40 bounded URL results (4 KiB each) beside the corresponding creation receipts. Under the same project lock, commit an unknown result before the first write. The original request returns its retained result without repeating writes; a changed public URL digest conflicts. Keep each result while its creation receipt survives, and remove it only in the same owner commit that evicts that receipt. Missing or expired creation receipts never authorize URL mutation.

If only one field succeeds, return remote_instance_url_incomplete with that operation/request and individual write/readback results. If incarnation changes, return instance_incarnation_changed and stop further writes. Never roll back another instance, infer success from an exit status alone or erase evidence of a partial write.

## Cleanup and retry

Creation receipts never add cleanup rights. Reused instances are never cleanup-owned. Created relation alone is insufficient: existing cleanup still requires the original operation terminal, current exact ownership independently verified and explicit deletion authority. Nonterminal or unknown original work blocks deletion.

Preview failure may clean up only its already-authorized exact route/DNS resources through existing behavior. Record configured, removed, cleanup_failed and unknown effects independently. Retain the selected instance and data when ownership/cleanup authority is not proved. No broad rollback.

A same request replay returns retained status or typed unknown/expired evidence after receipt eviction; it does not repeat initialization, URL writes or effects. Its permanent guard remains after instance deletion. Changing the bound intent refuses before effects even when detail is expired. Any separately authorized continuation must use its existing command and explicit relation to the original operation, with exact incarnation revalidation.

## Acceptance

Use the supported CLI/runtime chain for both WordPress and generic Compose with two labelled instances and distinct sentinel data/URLs. Observe created/reused cases, a lost response after pending commit, failed generic startup with retained ownership, a pending original child, changed incarnation, and one successful/one failed WordPress URL write. Require unchanged context propagation, pure capability/receipt queries, pre-effect unsupported refusal and a positive generic exposed-delivery result when all declared proof passes. Also evict receipt detail, inspect guards after a separately authorized instance deletion where available, fill guard capacity and interrupt between guard/registry commits: reused old keys stay unknown/expired/conflicting with zero replay, guards survive, and new keys at capacity refuse. Change each bound creation intent dimension under the same key and require pre-effect conflict. Required results are exact request/intent/incarnation joins, zero unrelated changes and zero new cleanup authority. Registry/diagnostic snapshots and supported readback prove the result; a green unit fixture does not substitute for authorized runtime acceptance.
