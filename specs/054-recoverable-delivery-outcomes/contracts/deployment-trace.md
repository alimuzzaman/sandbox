# Contract: Deployment Trace v1

This contract implements FR-029–034 and SC-010–011. It extends Feature 054 with a full-command diagnostic trace. Existing operation, admission, activation and recovery authority remain separate. The first producer is Lenzora's existing hosted deployment command; the mechanism and public query belong to Sandbox.

## 1. Owner and cross-language boundary

Use a separate owner-managed SQLite database at runtime/delivery/traces.sqlite3. New Python units are trace_models.py, trace_repository.py, trace_service.py and producers/{manifest.py,lenzora.py} beneath sandbox/delivery/. Register trace capability and producer descriptors through sandbox/delivery/manifest.py and the explicit existing CLI/MCP manifests. No new dependency, arbitrary executable registration, query-time project import, plugin process, application-state JSON reader, controller discovery or network mutation is allowed.

The producer manifest is compiled Python source. A descriptor has producer_id, producer_version, projection_schema, supported_stages and a fixed decoder callable. Initially it contains only lenzora-hosted-v1, version 1, projection schema 1. Adding another producer is an explicit source/manifest change. A query cannot supply a callable, module, executable, filesystem locator or alternate decoder.

Lenzora pushes a closed projection while its already-authorized command or worker executes. Its TypeScript trace adapter calls the existing readDeploymentRun, readSavedContext, receipt/preparation validators and private file owner APIs; it never bypasses their path, size, checksum or immutable-publication checks. Sandbox receives structured data, not a path from which to read those records. The fixed Python decoder independently checks its schema and deterministic request relationships. Query uses retained projections plus injected native read-only job, activation, delivery and recovery owner services. It executes no project code.

Projection provenance has two values: producer_recorded and owner_verified. A well-formed producer report records what that producer reported; it is not proof that a job, activation, runtime or deployment succeeded. Native owner joins separately verify those claims. Unverified IDs are retained only as explicitly unverified candidates and cannot establish historical success.

## 2. Identity and bootstrap

Before collecting the first preflight result, a valid supported invocation creates a UUID trace_request_id in the existing Lenzora private-state owner as an immutable invocation ticket. The ticket contains schema_version, trace_request_id, project_root_digest, producer_id/version, requested target/revision, mode and created_at; no command, environment, credential or default-file payload. Use files.ts publication/readback under traces/UUID/invocation.json. If the state owner or Sandbox trace executable is unreachable, report trace_unavailable; do not invent a retained trace_id or start protected work.

Resolve the configured Sandbox executable using a new read-only bootstrap helper that reuses inspectDeploymentDefaults. This resolution is not a passing preflight, does not publish defaults, and does not require clean source, all tools, installed remote runtime or authentication. A safe saved executable can still be reached when Git is unavailable. If defaults/binary/bootstrap is unavailable, collect and report all other preflight checks that can run, with trace.state=unavailable. A non-preflight command refuses before effects. Missing Node before TypeScript entry produces an explicit launcher trace-unavailable message; no retained trace is claimed.

The owner creates a random canonical UUID trace_id in the same transaction as the trace-request guard and initial document. Only a validated acknowledged/read-back result establishes that ID. It is distinct from the later release-bound requestId, stageRequestId, activationRequestId, job IDs and DeliveryOperation.operation_id. New command invocations may use new trace-request IDs while referring to the same existing run. No trace identity creates or replaces a workload request.

Scope is canonical project identity plus canonical root digest, producer_id and requested environment/label. The original project is the control project from which the command runs; application source/root is a separate later link. Trace lookup requires that original project directory. Remote, application revision, target incarnation and installed controller may be unknown before preflight. Unknown values are null with a reason, never wildcard authority.

Lookup identity is narrower than frozen intent scope: enforce unique locators (canonical project identity/root digest, trace_request_id) and (canonical project identity/root digest, trace_id). The guard stores the original producer and requested target scope, so inspect can recover it before target resolution without caller-supplied producer/environment. Reusing that project/request locator with a changed producer or target returns trace_request_conflict, never a second scoped trace. Parent lookup similarly uses project identity/root + producer + deterministic parent_request_id and retrieves its frozen target scope from the owner guard. Lookup does not grant wildcard target authority.

## 3. Public CLI and MCP

All CLI JSON modes emit exactly one JSON document to stdout. Progress goes to sanitized stderr; child stdout is captured/validated, never forwarded into the envelope.

~~~text
sb delivery trace-capabilities --json
sb delivery trace-start --project-dir DIR --trace-request-id UUID --input-json JSON --json
sb delivery trace-record --project-dir DIR --trace-id UUID --mutation-id UUID
  --expected-sequence N --input-json JSON --json
sb delivery trace-owner-status --project-dir DIR --producer lenzora-hosted-v1
  --parent-request-id ID [--publication-id UUID] --json
sb delivery trace-owner-record --project-dir DIR --producer lenzora-hosted-v1
  --parent-request-id ID --publication-id UUID --expected-sequence N --input-json JSON --json
sb delivery inspect --project-dir DIR (--trace-id UUID | --trace-request-id UUID) [--json]
~~~

trace-capabilities is read-only and does not create state. It returns schema_version=1, ok, capability="deployment_trace_v1", capability_version=1, runtime_revision, producer descriptors without callables, and the limits below. Its executable is the same controller executable used for trace-start/record/inspect.

trace-start and trace-record accept UTF-8 JSON argv values up to 32 KiB, reject NUL, unknown fields and non-finite values, and are diagnostic writes. There is no input-file, shell, eval, producer-path or remote-write option. Arguments are passed as argv elements using execFile/run_test_process, never shell-built. They have a ten-second caller bound; unknown acceptance uses the lookup procedure below. Public command handlers use registered CommandSpec and injected services.

Trace query selectors form a separate discriminated grammar. They cannot be combined with --remote, --environment, --label, --operation-id, --request-id, --observe, --limit or --cursor. The legacy operation query still requires its original non-null remote plus environment-or-label and keeps its existing QueryProjection unchanged. Do not make legacy query_scope fields nullable. Trace query dispatch validates its own TraceQueryProjection before default compatibility writers.

MCP exposes delivery_trace_capabilities(), delivery_trace_start(project_dir,trace_request_id,input), delivery_trace_record(project_dir,trace_id,mutation_id,expected_sequence,input), and extends delivery_inspect with optional trace_id/trace_request_id. The old required remote parameter becomes optional only at the Python function signature; the discriminated operation-query validator still requires it for all old calls. Existing old defaults are accepted only when not explicitly incompatible with a trace query. CLI and MCP use the same services, models, bounds and meaning.

Also expose delivery_trace_owner_status(project_dir,producer,parent_request_id,publication_id=None) and delivery_trace_owner_record(project_dir,producer,parent_request_id,publication_id,expected_sequence,input). Owner-status is a read-only sequence/projection/publication receipt lookup, not a job-status call. Owner-record accepts the same 32 KiB bound and version/context envelope as trace-record, with payload kind=projection or kind=stage. Parent stage payload is exactly role (prepare_job/activation_job), original job_request_id, stage, status, effect_state, reason and references. It cannot create a parent record: a validated trace-record projection must first atomically register/link the parent under the initial trace.

Writer result, including replay, is exactly schema_version, ok, code, trace_id|null, trace_request_id, sequence|null, document_digest|null and reason. Codes include created, recorded, existing, trace_request_conflict, trace_expired, trace_capacity, trace_store_unavailable, trace_contract_invalid, trace_sequence_conflict, trace_revision_unsupported and trace_acceptance_unknown. Reader transport/selector failures return ok=false; a serviced trace query about a failed command has ok=true.

For trace-record, trace_request_id is loaded from the retained trace owner; it is never a fresh caller value. Owner-record has a separate closed response: schema_version, ok, code, producer_id, parent_request_id, publication_id, sequence|null, document_digest|null and reason. Owner-status returns schema_version, ok, error|null, producer_id, parent_request_id, record|null, publication_receipt|null and coverage. Add trace_owner_conflict, trace_owner_expired and trace_owner_missing to the closed codes; owner lookup never chooses one arbitrary invocation trace.

W11's strict preflight schema gains one optional trace field: state (retained/unavailable/acceptance_unknown), trace_id|null, trace_request_id|null, reason {code,message}, and inspection selectors|null. Old reports remain readable. Normal --json gains a closed DeploymentCommandResultV1 envelope: schemaVersion=1, mode (preflight/deploy/legacy_projection), ok (command result only), trace, preflight|null, parentRequestId|null, commandResult, deploymentResult, reason. Existing normal text remains text, with the trace selector shown. No stdout prefix is allowed in either JSON mode.

## 4. Closed input and retained schemas

All identifiers/revisions/digests/reasons use existing delivery codecs unless narrowed here. Strings are capped before redaction; no raw paths, secret names/values, private argv, request bodies or arbitrary exception messages are public or retained. A source root is represented by its existing nonsecret identity/digest.

TraceStartV1 has exactly:

| Field | Type and rule |
|---|---|
| schema_version | Exact integer 1 |
| producer | {id: lenzora-hosted-v1, version: 1, projection_schema: 1} |
| mode | preflight, deploy or legacy_projection; the last accepts diagnostic export only and cannot enter protected stages |
| requested_target | {environment: Identifier, remote_name: Identifier or null}; environment is known from valid args, remote may be unresolved |
| requested_source | {revision: full Git revision or null, policy: retained_verified_artifact}; null means selection has not occurred |
| producer_context | {source_commit: revision or null, source_digest: Digest or null, node_version: bounded version or null, state: known/partial, reason: SafeReason} |
| expected_runtime_revision | The trace-capabilities runtime revision, not the installed remote revision |

The owner computes project identity/root digest and controller source/runtime revision. It does not trust these as caller input. Dirty or unavailable producer source is allowed at start and remains explicitly partial; existing protected clean-source checks still run during preflight. Source_digest is a bounded digest of the fixed integration-owned source files when available, not a traversal of the project or environment.

TraceDocumentV1 has schema_version, trace_id, trace_request_id, intent_digest, project_identity, project_root_digest, producer, requested, producer_context, controller_context, sequence, created_at, updated_at, finished_at|null, lifecycle, command_result, deployment_result, stages, events, omitted_events, parent_link|null, owner_projection|null, candidate_links, recording_gap|null, terminal_digest|null. No unknown fields.

controller_context separates source_commit, source_runtime_revision and installed_controller_runtime_revision|null. The latter is first supplied by the validated preflight/registered-controller read, never inferred from local equality. The immutable intent covers original project, producer, mode, requested target/source and initial controller/producer context. Later resolution may fill a previously unknown contextual field through an identity observation; it cannot overwrite a known value.

The first retained parent link is immutable. Later projections must preserve its producer, parent request and identity digest. A projection release revision must match a known requested application revision; a later application identity observation must also match an already retained run. Conflicts are rejected atomically before creating or updating parent records.

Lifecycle is open, terminal or unknown. command_result is not_finished, succeeded, failed, interrupted or unknown. deployment_result is not_started, incomplete, succeeded, failed or unknown. A preflight-only success has command_result=succeeded, deployment_result=not_started and no workload child. An active or uncertain child prevents a requested deployment from becoming succeeded, even if the wrapper command exited. A terminal command snapshot is immutable; later query-time child/recovery observations are separate and cannot rewrite it.

Stages are a map with exactly bootstrap, preflight, release_selection, artifact, checkout, prepare, stage, activation, runtime_verification, public_verification and recovery. Each contains status (not_started/running/succeeded/failed/unknown/not_applicable), first_at|null, last_at|null, provenance, reason, references (at most four) and effect_state (not_started/entered/observed/failed/unknown/not_applicable). Recovery is a relation/observation stage, not permission to run recovery. A later separately authorized recovery does not change original terminal stages; the query reports it separately.

Events retain the last 64 observed transitions. Each has seq, at, stage, status, effect_state, provenance, reason and at most four safe references; at most 1 KiB encoded. The owner assigns seq and recorded timestamp; producer-observed time may be included only inside a closed observation with source and is never substituted for owner receipt time. Fixed producer stage order is bootstrap -> preflight -> release_selection -> artifact -> checkout -> prepare -> stage -> activation -> runtime_verification -> public_verification. A stage may be skipped only with an explicit not_applicable contract reason. Unknown is not a passing transition. Repeating an identical stage/effect observation is a no-op event-wise. Historical empty timelines stay empty.

Stage order applies within a single invocation, not across concurrent parent publishers. Allowed status transitions are not_started -> running/failed/unknown/not_applicable, running -> succeeded/failed/unknown, and unknown -> running/succeeded/failed only after an explicit retained owner observation resolves the same original reference. Succeeded, failed and not_applicable are absorbing for that invocation; an identical observation is a no-op and a contradictory transition conflicts. A resumed invocation may attach older verified child proof without inventing earlier invocation transitions: unobserved earlier stages remain unknown with history_unavailable, or not_applicable only where the invocation contract truly excludes them. Query-time proof enrichment stays in owner_evidence. It never erases a frozen failed stage or terminal command result. ProducerRunRecord publication merging has no global phase cursor; its immutable identity and monotonic per-role rules below govern concurrent updates.

TraceRecordV1 is exactly schema_version=1, producer_context, expected_runtime_revision and one discriminated payload:

- kind=stage: stage, status, effect_state, reason, references. This records producer progress; it cannot set owner_verified.
- kind=projection: projection is the fixed ProducerOwnerProjectionV1 below. The owner validates deterministic relationships and records the snapshot plus its canonical digest.
- kind=identity: one nonsecret resolved context block (producer source, selected remote/controller, selected application source); known values cannot change. Required protected-stage recording refuses if frozen known producer source or controller runtime differs.
- kind=finish: command_result, requested_deployment_result, reason. Sandbox computes the retained deployment result from validated required evidence; requested_deployment_result is a claim and cannot force success.
- kind=gap: stage, effect_state, reason, original safe workload references. It never authorizes continuation.

Changes to runtime revision or a known source identity return trace_revision_unsupported. Unknown source becoming known after successful preflight is one allowed identity observation. A dirty preflight refusal needs no clean identity. A writer from a new revision can read old trace/guard state but cannot silently continue the old invocation's recording context; a new invocation may attach the same validated existing run.

## 5. Lenzora owner projection and verified joins

ProducerOwnerProjectionV1 has exactly schema_version=1, producer_id, producer_version, projection_kind (current_run/legacy_run), observed_at, preflight|null, run|null, control, artifact|null, phase_jobs, native_receipts and terminal|null. It is at most 32 KiB. The retained trace keeps the latest accepted projection and digest; older transition events refer to their observation digests without implying full snapshots were retained.

- preflight contains mode, target, requested_revision|null, ok and at most 16 checks. Each check has the existing fixed check ID, passed/failed/blocked, fixed code, version/revision observations only, and blocked_by IDs. Strip path and arbitrary action/message fields. The Python decoder independently validates check IDs, dependency references and overall ok.
- run contains the exact existing release selection (target/revision/branch/run_id/run_attempt/artifact_id/artifact_name), receipt_digest, generation, parent_request_id, stage_request_id and activation_request_id. Python reconstructs the current state.ts canonical identity from the exact field order and JSON encoding: domain lenzora-hosted-deployment-v1, release using its TypeScript field spellings/order, receiptDigest and generation, SHA256 first 40 hex. It validates the lenzora-dev/lenzora-prod prefix, parent and suffix IDs. Shared golden JSON byte fixtures establish cross-language equality before integration acceptance.
- control contains source_commit|null, root_digest, producer_source_digest|null and state/reason. This is the wrapper source, not application source.
- artifact contains policy=retained_verified_artifact, revision, receipt_digest, plan_digest|null, proof_digest|null, configuration_digest|null and up to 32 manifest digests. Each supplied digest must come through existing receipt validators. Larger valid native sets are partial with a generation/proof reference, not truncated.
- phase_jobs has at most two entries: role prepare_job or activation_job, job_id, request_id, control_root_digest, control_source_commit, submission_digest and state/reason. Request IDs must be parent_request_id + "-prepare"/"-activate". submission_digest is a producer-recorded candidate independently recomputed by the job owner over retained role-relevant submission fields; private argv never enters the trace. Hash UTF-8 canonical JSON with recursively sorted object keys, no ASCII escaping, compact separators and no non-finite values, prefixed with sha256:. Its object is {domain: lenzora-hosted-job-submission-v1, role, request_id, control_root_digest, control_source_commit, command_digest}; command_digest hashes the exact private argv JSON array with the same encoding. A matching supplied digest alone never proves command binding: the native owner also validates the fixed worker role and retained submission.
- native_receipts has at most 16 closed references, role stage_request/activation_operation/runtime/public_verification/recovery_operation, original request ID and applicable operation/generation/plan/proof/config/target digests. Claims remain unverified until native owners match them.
- terminal contains only original activation request, command code, claimed outcome and existing receipt digest; query/finish evaluates native owner evidence independently.

The prepare job request is parent + "-prepare"; it is deliberately distinct from stage_request_id, which is parent + "-stage". The activation job request and activation request both use parent + "-activate" in the existing W11 algorithm, but retain separate owner roles. Namespace equality never makes a job an activation result.

Extend the job owner's read-only projection with read_trace_job_evidence(job_id) returning exact job/request/project/root/source, lifecycle/exit/times, command/submission digest and output completeness, never argv or environment. The trusted fixed Lenzora decoder compares the expected phase request and control source/root, then the job owner validates the stored command/submission binding using a fixed role descriptor and canonical digest; no caller-supplied command is executed or treated as proof. Missing legacy command-binding evidence is partial, not a match. Do not use JobService.get/reconciliation or validate_durable_context to fill this link.

Job evidence uses a private in-memory snapshot without connecting SQLite to owner paths. A single bounded capture validates file identity, two matching byte reads, and the existing duplicated, checksummed WAL-index published head. WAL version 3007000, generation salts, the selected frame checksum chain, and its final commit size must match before replay into private memory. Physical frames after the published head never supply evidence. Missing or changed sidecars, unsupported formats, unsafe paths, corruption, and cap/deadline failures return partial; the reader never recovers or locks the owner. A checkpointed base with absent or empty WAL is supported. The adjacent ordinary delivery job reader uses the same mechanism with a finite standalone budget.

Activation links require original activation request, exact target/registered host/environment, parent release source/artifact/config/plan/proof, and generation from existing validated activation owner reads. A same request-shaped string alone is insufficient. Ordinary application jobs continue to join C through admission; prepare/activation wrapper jobs join control source and are never copied into DeliveryOperation.job_id. Producer snapshots can establish recorded selection but not observed runtime revision or authoritative terminal delivery.

Implement read_trace_activation_evidence(request_id, scope, deadline) in sandbox/hosting/images/activation/status.py over a new bounded owner read in sandbox/hosting/recovery/repository.py. Its closed result includes original request, target/project/registered-host/environment digests, selected source revision and signed manifest digests, generation, configuration/plan/proof digests, original timestamps, initializer result, independently observed runtime source/images/health and required public/edge results, with completeness for each dimension. Decode through the existing activation owner codecs; missing legacy dimensions remain partial. The current read_delivery_status result and generation digests alone cannot prove these joins. An exactly joined retained DeliveryOperation may supplement only the specific dimensions it actually retains, with its provenance/time. Do not substitute requested source for observed runtime source. For schema-v2 service image references, validate the native generation first, then extract only the manifest digest after @; image sets above the delivery limit of 32 produce partial proof plus an owner generation/proof reference, never truncation or a raised public limit.

Lenzora calls its projection adapter after readDeploymentRun resolves an existing run and after original job/receipt boundaries in cli.ts, job.ts, native.ts and worker.ts. Main first uses trace-record to register a stable ProducerRunRecord and attach its exact parent key. Workers keep precisely their existing phase/directory argv, existing phase request IDs and submission bytes. They derive the same parent ID through readDeploymentRun and publish with trace-owner-record; no per-invocation trace ID or mutable active-trace pointer enters worker arguments or workload digests. A new invocation trace can attach the same ProducerRunRecord. Main/finally alone records its own command result; if main disappears after a child commits, command result remains unknown while the separate child result is committed.

ProducerRunRecord is keyed by project scope + producer + parent_request_id. It has immutable intent_digest over release/receipt/generation/parent/stage/activation IDs and saved control root/source, its own sequence/created_at/updated_at, retained projection, 64-event ring, omitted_events and up to 256 publication receipts. Registering and linking the first parent from trace-record is one trace-store transaction. At most 32 candidate/verified role slots and 16 recovery links are retained; query expands at most ten recoveries. Existing parent intent or non-null immutable role identity cannot be changed by another invocation.

The parent also retains role_stages with fixed prepare_job:{prepare,stage} and activation_job:{activation,runtime_verification,public_verification} maps using the stage codec and absorbing terminal rules above. A stage publication must match the saved control identity, deterministic job request and allowed role/stage pair; validation does not infer native success from an effect-enter claim. Before native prepare/stage/activate effects the worker commits/readbacks the corresponding parent stage-enter using owner-record and its stable publication ID. It stops on missing/expired parent or definite/unknown recording failure, preserving original job authority. These parent transitions share the bounded parent event ring; the query exposes them separately as owner_evidence.parent_stages, with omitted/partial coverage, rather than fabricating main-invocation events. This satisfies pre-effect recording without changing worker argv or request IDs.

Owner updates use the same publication-ID-before-CAS replay rules as trace-record. Empty/null/partial fields from an older snapshot never erase known fields, links, proof or terminal child outcomes. Known immutable non-null disagreement is trace_owner_conflict; same publication with changed content conflicts. For the same identity, producer running/unknown observations cannot replace a retained verified terminal receipt. Receipt/link enrichment is monotonic; recovery adds a separately keyed relation and never replaces the original failed role. A stale expected_sequence consumes no receipt; the producer reads owner-status and retries the identical publication content/ID only if a monotonic merge remains valid. Sandbox revalidates native proof on query; producer claims never promote themselves to owner_verified.

Each owner-record call is bounded by ten seconds. Unknown acknowledgment is resolved by owner-status with the original publication ID; a missing receipt permits the same-ID replay after a conclusive read, never a fresh publication identity or workload replay. For deterministic boundaries, publication IDs are UUIDv5 over the existing parent request + producer version + phase + bounded boundary name + canonical content digest, so retries/reconnects derive the original identity without altering worker argv. A new content observation has a different publication identity; it must still pass the monotonic merge.

Legacy projection is an explicit diagnostic export performed by the supported producer command during an authorized local read, then submitted to trace-start/record as projection_kind=legacy_run. It may use readDeploymentRun and existing validators. An ordinary Sandbox inspect never launches that export. Legacy trace coverage starts at the earliest actual retained evidence; preflight and earlier artifact history remain unavailable. The export does not stage/build/activate or alter old run, job or terminal bytes.

## 6. Transaction, replay and failure semantics

trace-start atomically reserves a permanent deny-only guard and the initial document, then reads both back before returning created. Guard key is a domain-separated digest of canonical project identity/root + trace_request_id, with a unique project/trace_id locator. Guard contains trace_id, trace_request_id, frozen producer/target scope, intent_digest, reserved_at and detail_state (present/expired/unknown), at most 1 KiB. There are 4,096 guards per controller shared with parent guards. Identical retained start returns existing; changed intent/producer/target under the same locator returns trace_request_conflict; evicted detail returns trace_expired and never creates a replacement under that key. Guards confer no workload authority.

The producer persists its invocation ticket before calling start and keeps that original trace_request_id throughout the invocation. Empty, malformed, timed-out or mismatched response is trace_acceptance_unknown, with no claimed trace_id and no dependent effects. It performs one supported inspect by the original trace_request_id; if found and intent matches, resume recording that trace. If conclusively absent, it may replay the identical start once under the same key; if still ambiguous, stop with original lookup selectors. Never use a new request ID as an acknowledgment retry. A new user invocation is separate and can link the same retained workload run.

trace-record uses a monotonic expected_sequence and immutable mutation_id. In one transaction it checks an existing mutation guard first, then compare-and-swap sequence, validates the new document, writes the record and mutation guard, and reads the result back. Same mutation/payload returns its original acknowledgment without a second event; changed payload conflicts. expected_sequence is not part of mutation content digest. A sequence conflict consumes no guard: read the trace, then retry the same mutation/content with the new sequence if the state transition remains valid. A lost record acknowledgment is resolved by read-only inspect using trace ID and the retained mutation ID in the query's mutation receipt field; no workload command is rerun. At most 256 mutation receipts per open/terminal trace; reaching that bound refuses further new records before dependent effects. Receipt detail may expire only together with terminal trace detail; the permanent start guard survives.

Writer/publication receipt document_digest is the canonical digest of the snapshot accepted by that original mutation, before later mutations or query enrichment/elision. Replays return that original digest and accepted sequence. It is not the digest of today's query trace, and callers must not compare it to an enriched projection as acknowledgment validation. Trace start uses its initial accepted snapshot under the same rule.

Before each first or next protected phase, commit/read back the required stage-enter record. A definite or unknown recording failure stops the next protected effect. If an external effect has already started/committed when a later record fails, preserve the existing run/job/activation/recovery owner records, return the original IDs and trace_record_incomplete, and stop further dependent effects. A later diagnostic projection can report the existing owner evidence as a separate observation; it cannot claim the missing event was retained at the earlier time. No cross-store atomicity or auto-recovery is claimed.

Finish stores an immutable terminal command snapshot and digest. Same terminal replay is a no-op; different terminal input conflicts. Unknown/lost wrapper completion remains unknown/open rather than a manufactured failure or success. A trace whose command ended while an authoritative child remains active/uncertain is protected for retention; queries continue showing its current recorded owner evidence separately. No query marks it cancelled, reconciles it, or removes its protection. Writer-side protection reconciliation may clear protection only after the same original owner read proves every linked child terminal; unresolved/missing identity stays protected.

## 7. Retention and query bounds

The internal writer scope may carry owner_observation with exactly
joined_deployment_result, completeness and children_terminal. Only TraceService
computes this value from the original bounded owner reads; it is absent from every
public input. Complete proof with all children terminal permits writer-side
protection reconciliation. The reconciliation changes retention metadata only for
existing terminal traces; it never rewrites their command or deployment snapshots.

The trace store uses a two-second SQLite busy bound, a 128 MiB database cap and at most 128 MiB rollback space. Writers check capacity before committing. There are at most 128 open/uncertainty-protected traces, 512 unprotected terminal traces globally, 64 unprotected terminal traces per original project/producer/requested-target scope, and 30-day terminal detail. Per document maximum is 128 KiB, per producer input/projection 32 KiB, links 32, stages 11, event ring 64, event bytes 1 KiB and mutation receipts 256. Permanent start guards are never pruned. No reset/namespace rotation is introduced to reopen used IDs.

ProducerRunRecords share this byte cap; they are not an unbounded side cache. They have independent maxima of 128 protected and 512 unprotected records, 64 unprotected per project/producer/environment, at most 128 KiB each and 30-day terminal detail. A parent remains protected while any retaining trace or validated child is open/uncertain. Writer-only retention can evict an unprotected parent's projection/events/publication receipts with explicit expired coverage; a compact parent intent guard, within the shared 4,096 guard budget, remains deny-only. Expired owner-record writes refuse trace_owner_expired. A new invocation may retain a fresh legacy_run projection inside its own trace and use native read-only joins to the same old run, but cannot reconstruct the expired parent's timeline or reopen its publisher. All row/count/byte bounds are maxima; the byte cap can refuse earlier.

Queries read existing diagnostic databases in mode=ro and native job snapshots in private memory. They never create owner stores, migrate, reserve, prune, reconcile or lock an effect transaction. A missing store is an explicit serviced missing result. All native owner reads are local, bounded and read-only; aggregate query budget is five seconds, output 256 KiB. An unavailable or timed-out owner is partial with reason and original reference, not success. Current network runtime observations remain on the existing separate --observe operation path; trace queries do not add them.

Job snapshot capture permits at most 32 MiB of combined database/WAL source bytes, a 32 MiB reconstructed image, and 65,536 selected frames. Source reads use at most 64 KiB units with deadline checks around reads, checksum/application units, deserialization, and queries. The private image never spills to a scratch database. These are diagnostic coverage caps, not job retention limits. Stable WAL and normal WAL reuse must remain visible within the caps; unsupported or changing captures remain partial.

TraceQueryBudget carries one monotonic deadline from service entry into every injected owner read, loop and serializer; it is never reset per join. SQLite uses timeout=min(2 seconds, remaining), a progress handler that interrupts at deadline, bounded SELECT counts and pre-decode row byte limits. The new activation/recovery trace reader checks regular-file ownership/size (maximum 8 MiB), reads no more than cap+1 bytes, checks the same deadline before/after the read and decode, then invokes existing closed owner decoders. It does not call the current generic RecoveryRepository.load/json.load path, whose size/read is unbounded. Preserve that unrelated API's behavior. Check deadline before/after every bounded JSON decode and each of at most 640 related-record scans; stop remaining joins with explicit budget_exhausted partial coverage. No thread is left reading after a timeout; no unbounded callback, blocking network call or detached worker is permitted by these ports. The byte/count caps bound individual synchronous decode units; the aggregate bound is five seconds plus at most the in-flight bounded local decode and final bounded serialization, and acceptance records that measured overrun explicitly rather than promising hard preemption.

Reverse recovery lookup stays in DeliveryRepository: validate at most 640 retained operation documents (512 terminal + 128 protected) joined through permanent request scope; match original_delivery exactly and verify same project/root/remote/target-kind/environment-or-label. Return at most ten newest summaries. Overflow, bad record, expired original/child detail or store unavailability is explicit. Even an empty bounded list means no retained matching child was found, not that recovery never occurred. It never modifies the original terminal document. If selected original detail expired, its owner-returned guarded operation ID can still select related records, with original completeness expired.

## 8. Trace query envelope and evaluation

TraceQueryProjectionV1 is a separate closed object: schema_version=1, query_kind=deployment_trace, ok, error|null, query_scope {project_identity,project_root_digest,trace_id|null,trace_request_id|null}, recorded_at, observation_mode=recorded_only, trace|null, owner_evidence, recovery_operations, mutation_receipt|null, coverage and next_action|null. trace uses TraceQueryDetailV1, not the storage codec: it has every TraceDocument field with identical required identity/outcome/stage types, but owner_projection is nullable, events may be a shorter suffix, and the additional required detail_coverage object contains retained_document_digest, projection (included/omitted/not_recorded), retained_events, returned_events and omitted_events. Storage documents are never passed through this elidable codec or written from it. owner_evidence is {summary,links,parent_stages}; parent_stages contains the fixed role_stages map or null plus completeness/reason. summary contains joined_deployment_result (not_started/incomplete/succeeded/failed/unknown), completeness and reason, while links contains at most 32 role evidence rows. Each row has role, request_id|null, job_id|null, operation_id|null, source_role (control/application/original_deployment), state, result, provenance, observed_at|null, proof_digest|null and reason. recovery_operations has completeness, omitted and at most ten existing operation summaries. coverage contains trace_state, owner_state, early_history (recorded/unavailable), omitted_events, omitted_links and reason. It never reuses the legacy remote-required query_scope codec.

For lost-record lookup, inspect additionally permits --mutation-id UUID only with --trace-id; MCP adds mutation_id with the same restriction. It returns only that mutation's ID, content_digest, accepted_sequence and document_digest, or an explicit missing/expired receipt. It does not expose every mutation guard or accept mutation as lookup authority.

Each role evidence row additionally has required detail: TraceRoleEvidenceV1 or null with state/reason explaining absent detail. TraceRoleEvidenceV1 is a closed object of source, artifact, target, generation, configuration, initializer, runtime, public_verification and job blocks. Each block uses the existing common evidence fields (source_kind, observed_at, target_digest, applicability, state, result, reason) plus only its named payload: source {requested_revision,observed_revision,control_revision,source_artifact}; artifact {policy,receipt_digest,plan_digest,proof_digest,manifest_digests}; target {registered_host_digest,environment,incarnation_id}; generation {generation_id,digest}; configuration {digest}; initializer {status,receipt_digest}; runtime {source_revision,image_digests,health,verification_digest}; public_verification {hosts,edge_state,edge_proof_digest}; job {submission_digest,started_at,finished_at,exit_code,output_complete}. Payload scalars are nullable with completeness reasons, host rows are bounded existing route-evidence objects, and image/host collections keep the existing 32/20 maxima. No arbitrary native dictionary passes through this codec. A role detail is at most 16 KiB; combined response still has the 256 KiB cap. This carries the exact native proof to JSON/MCP/human output. An elided detail becomes null with explicit omitted coverage and cannot leave joined_deployment_result=succeeded where that proof is required.

Optional detail is removed before serialization in this order: set owner_projection=null with projection=omitted, omit optional role/recovery rows while counting omitted links/children, then retain a shorter event suffix and update detail_coverage. Every field of each remaining closed object stays present; never remove a required property. Keep identities, all required gap/outcome/stage/coverage fields and safe digests. Never byte-truncate JSON or retain a joined succeeded claim after its required proof was omitted/unavailable. A retained historical command/deployment result remains unchanged and explicitly separate from query-time joined_deployment_result and its completeness. If the mandatory minimum envelope alone exceeds 256 KiB, return a bounded trace_contract_invalid query error with trace selectors and no embedded detail.

Human output starts with command result, joined deployment result and furthest proved stage. Then show original trace/parent/request/job roles; project/environment/remote and application/control/artifact distinctions; times and bounded timeline; exact observed runtime/generation/images/initializer/routes/edge; and separate recovery links. All unavailable/null values are explicit. Inherited recovery control/application metadata is labelled original deployment metadata.

Next actions are read-only templates on the same Sandbox executable/controller/home. Preserve the two output corrections in diagnosis.md: complete failure gives no missing-proof loop; complete nonterminal gives authority_pending; an offered read does not erase a frozen failure stage. Use shlex.join and --project-dir . with explicit project cwd/absolute executable guidance. No action creates a request, rebuilds an image or supplies recovery/cleanup authority.

## 9. Python implementation ports

trace_models.py exports parse_trace_start(value), parse_trace_record(value), parse_trace_owner_record(value), parse_trace_document(value), parse_trace_query(value) and serialize_trace_query(projection, max_bytes=262144). ## 10. Compatibility and validation obligation

deployment_trace_v1 and lenzora_hosted_trace_v1 declare version 1 separately from delivery_outcomes_v1. Required producer decoder and executing Sandbox runtime revision are checked before new trace writes; installed target runtime remains a separate deployment preflight input. Older consumers retain old operation query behavior and old preflight reports remain readable. A new producer on an old controller reports typed trace_unavailable/unsupported and blocks dependent protected effects, never silently downgrades coverage.

All new source/config/docs across Sandbox and W11 complete before actual supported command acceptance. Literal preflight, retained-image full owner pipeline, lost start/record acknowledgments, wrong links/roles, source/runtime drift, legacy snapshots, expired guards, retention/capacity, image overflow, and immutable terminal bytes must be observed through actual CLI/MCP adapters on owned fixtures before regressions. Synthetic external ports do not prove remote/runtime deployment. Full required gates and independent correctness/product review follow those observations.
